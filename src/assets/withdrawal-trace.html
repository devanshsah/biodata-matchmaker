Withdrawal state machine⇆ scroll
The design point that matters here: when the custody provider's API call times out, the withdrawal does not fail and it does not retry blindly — it moves to UNKNOWN with funds still reserved. A reconciliation job re-queries the provider using the same provider reference, and only then resolves the state to SUBMITTED (accepted) or FAILED (confirmed not processed). This is what stops a network hiccup from becoming either a lost customer withdrawal or a duplicated one.

Key design points
IdempotencyEvery request carries an idempotency key; every provider call carries a stable reference. Retries can never create a second withdrawal.
AtomicityBalance reservation and status transitions happen together — a withdrawal is never "in flight" against an unreserved balance.
ReliabilityTimeout → UNKNOWN → reconcile, not timeout → FAILED. Truth comes from the provider, not from silence.
Key design points, continued
SecurityTLS everywhere, secrets in KMS, webhook signatures + timestamp/nonce checks to block replay.
ObservabilityEvery state transition emits an event; failed, stuck and reconciliation-failed withdrawals page someone.
User experienceReads are served from a dedicated read model so status polling never contends with the write path.
